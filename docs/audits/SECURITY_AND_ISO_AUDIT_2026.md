## 1. Executive summary and scope

Reviewed all 178 files under `supabase/migrations/` as source text, the generated public DB types, DAL/lib repositories, route guards, business switching, partner context/provider, React Query persistence and identity transitions, selected Edge Functions, audit logging and relevant business/plan permission code. `src/routes/PlatformAdminRoute.tsx` is not a separate file: its export is in `src/routes/ProtectedRoute.tsx`. No `partnerClientContext.ts` exists at the requested path (or elsewhere under `src/`); the related current implementation is `src/partner/PartnerContext.ts`, `PartnerProvider.tsx`, `PartnerClientRepository.ts`, partner admin pages and RLS helpers.

**Overall assessment:** the source has meaningful tenant boundaries—RLS is enabled broadly in migrations, business membership is usually re-derived in SQL, payroll has dedicated role helpers, admin RPCs re-check authority, and known same-tab user changes/logout clear query/SW/persisted caches. However, there are material source-level authorization and assurance gaps. The most consequential confirmed finding is generic member/write RLS that grants much broader financial read/write access than the UI role matrix. Manufacturing enterprise access is also gated in the browser but not consistently at SQL/RPC boundaries. Other residuals include full-row partner peer visibility, an identity-neutral persisted browser cache, and audit completeness/integrity limitations.

**Static inventory:** 178 SQL migration files; 167 textual `CREATE TABLE` matches; 351 textual `CREATE POLICY` matches; 139 textual `ENABLE ROW LEVEL SECURITY` matches; 465 textual `SECURITY DEFINER` occurrences (including replacements/comments); 409 textual `GRANT` matches. A source parser found 383 definer declarations across history and 321 unique latest signatures before removing the explicitly dropped legacy `assign_user_to_eagle_businesses`; the function register below contains 320 source-visible latest surviving signatures it could parse. Some checked-in migration filenames are dated after the audit date; they are reviewed as source only and are not presumed applied. Counts are source-text counts, not deployed catalog counts. Generated types include 146 public tables; generated types do not encode RLS, grants or view security mode.

**Confirmed vs conditional:** confirmed findings below are visible in migration/source definitions. Partner table SELECT ACLs, effective grants/default privileges, role ownership/BYPASSRLS, actual migration application order/status, live triggers not present in migrations, and production Edge Function configuration cannot be proven from this checkout. Those are labeled conditional or unverified, not assumed safe or unsafe.

## 5. Server-side authorization, plan enforcement, partner access and audit trail

### Confirmed positive controls

- `ProtectedRoute` enforces authenticated session for route rendering; `PlatformAdminRoute` is exported from that file and checks the hydrated platform-admin flag for UX. `PartnerAdminRoute` checks portal access for UX. Neither component is the security boundary; database policies and RPCs must re-check authority.
- `grant-manual-subscription` calls `auth.getUser()` with the bearer token and then checks `user_profiles.is_platform_admin` with a service-role client before writing payment/plan data. `list_all_businesses` and partner-admin RPCs similarly perform function-level authority checks.
- `effective_plan_tier` and `_ledgr_assert_usage_limit` enforce expiry/quota server-side for billable docs. Several construction quality/change-order/RFI and approval functions have explicit effective Enterprise checks. This is not universal enforcement for all new module functions.
- POS, accounting-period, payroll, invite, partner, and audit-related command paths contain SQL/RPC-level checks in many inspected migrations. Do not extrapolate those checks to all CRUD/table policies.

### Findings

**SEC-01 — High: generic business RLS is broader than the UI role matrix.** `is_business_member(business_id)` permits any active member to read tables in the Phase 8B generic family. `can_write_business_data` grants writes to roles including `inventory_manager`, `warehouse_worker`, `asset_manager`, `cashier`, `manager` and `stock_clerk` (as well as owner/admin/accountant and other operational writers). The Phase 8B loop applies this generic pattern to core financial tables including `journal_entries`, `journal_lines`, invoices, expenses, budgets and statements. Yet `src/hooks/usePermissions.ts` marks `canViewFinance=false` for inventory_manager, warehouse_worker, asset_manager, cashier, manager and stock_clerk; the database read helper still allows those members to select the generic-family finance rows, and the writer helper still permits several of those roles to insert/update them. `RoleRoute`/navigation are client-side and can be bypassed by calling PostgREST directly. The migration itself notes page access is the confinement mechanism for some reads and that a sales clerk can write journals/budgets at the database level. This is a confirmed authorization-model mismatch unless the product explicitly intends those roles to have these broad server rights. **Impact:** a valid tenant user with a narrower UI role can read or mutate financial data outside their UI tier through direct API requests; tenant isolation remains by business, but within-tenant least privilege fails.

**SEC-02 — Moderate: Enterprise manufacturing entitlement is not consistently enforced server-side.** The plan table and `useCapability` require Enterprise for `manufacturing`; source comment in `20261103000000_manufacturing_foundation.sql` says Enterprise plan gating is at workspace/UI level. But `provision_manufacturing_defaults` and `provision_manufacturing_coa_accounts` check owner/admin and MANUFACTURING operating model, not `effective_plan_tier`. The provisioning function creates `manufacturing.bom.manage`; BOM write RPCs and manufacturing work-order policies/commands enforce membership/owner-admin-manager, but no consistent Enterprise tier check is present in these paths. Authenticated users can call granted RPCs directly, bypassing the route gate. This is an entitlement/feature boundary gap, not an unauthenticated cross-tenant bypass.

**SEC-03 — Moderate: opt-in partner peer access exposes the entire business row, including tax/contact PII.** When `partners.allow_client_visibility` is true, `businesses_partner_peer_read` permits same-partner client users to SELECT sibling `businesses` rows; RLS is row-level, so it does not restrict columns. `businesses` includes TPIN/VAT/registration, address, email and phone, not only discoverable business name. The option defaults false and the migration says sibling discovery is opt-in, so classify as conditional-by-configuration and likely broader than intended, not as universally exposed. Review partner contract/consent; use a minimal view/projection or column privileges if only names/status are intended.

**SEC-04 — Moderate: persisted business query cache is not principal-bound at restore.** `src/lib/queryPersister.ts` persists the entire allowlisted React Query client to one fixed IndexedDB key `rq-state`; `businessId` is an unused optional field and not populated. `PersistQueryClientProvider` starts in `main.tsx` before auth hydration. `useAuthListener` wipes memory/persisted/SW caches on explicit sign-out and known same-tab identity changes, but a cold start has `lastHydratedUserId === null`; there is no persisted-cache principal tag checked against `auth.getSession()` before restore. Business switches do not clear the query client, relying on tenant IDs in keys (mostly present) and RLS on refetch. This leaves a prior identity's allowlisted data at rest and can hydrate it before the new user/role is known; exact visible impact depends on cache namespace, same-business membership/role, fetch timing and server headers. Do not claim a demonstrated exploit from static source alone. The Workbox API cache also uses URL/cache response semantics rather than an app-level principal tag; it is intentionally cleared on known transitions. Recommendation: gate restore until verified identity, namespace persisted cache by user + business, clear on any identity mismatch before rendering, and test reload/cross-tab/offline role changes with real browser evidence.

**SEC-05 — Moderate assurance gap: audit coverage/production fidelity cannot be established.** Phase 8B explicitly says audit RPC bodies and hash algorithm were reconstructed because production originals were not captured. The source `log_manual_audit_event` hashes fields but uses a fixed `0.0.0.0` IP and accepts caller-provided event labels/old/new/notes. Some critical updates are explicitly logged, and RLS limits audit reads, but there is no migration definition for `audit_employees`/`log_table_change()` despite `PayrollRepository.updateEmployee` documenting a full-row audit trigger. This makes employee audit coverage non-reproducible from this migration set; it may be out-of-band on a deployed database. Verify live triggers and existing data, then make the trigger/function migration-managed and redact sensitive old/new fields.

**SEC-06 — Low: filtered `verify_audit_chain` can report valid chains as invalid.** `verify_audit_chain(p_business_id,p_resource_type)` filters rows by resource type before walking the chain, then compares each row’s `prev_hash` with the previous returned row’s `entry_hash`. Intervening events of other resource types are omitted, so filtered runs generally fail the predecessor check despite correct full chain. The repository exposes the optional resource filter. This is a verification correctness issue, not a tenant bypass; verify full chain first or carry/validate the true predecessor sequence.

**Conditional ACL review:** `partners_public_read` uses `USING (true)` on a table that also contains billing contact/pricing fields, and `PartnerRepository.getBySlug/getByCustomDomain` requests `select('*')`. The intended pre-login branding path requires some public read, but the migration does not establish column-level separation. Because effective table grants/default ACLs are not fully determined from this checkout, do not count it as a confirmed anonymous disclosure until live `has_table_privilege`/`information_schema.column_privileges` checks. Remediate by exposing an explicit branding view/projection and keeping billing fields behind partner/platform-admin access.


## 6. Audit logging, diagnostics, cache/session and partner-context review

### Audit/logging

- `audit_log` table has RLS enabled; Phase 8B grants SELECT through `can_read_audit` (owner/admin/accountant/payroll_manager/auditor/board_member) and platform-admin read. No direct client insert/update/delete policy is intended; authenticated app paths use SECURITY DEFINER logging RPCs and privileged DB paths/triggers.
- `log_manual_audit_event` derives `user_id` from `auth.uid()` and requires `can_write_business_data`; `verify_audit_chain` requires `can_read_audit`. Hash helper execute is restricted to `service_role`. Those are good boundaries, but audit completeness (SEC-05), IP provenance and filtered verification (SEC-06) remain concerns.
- `src/lib/logger.ts` defaults production to warn+, but caller-supplied context/message/Error objects can be emitted to browser console and Sentry. `main.tsx` sets `sendDefaultPii:false`, removes cookies and clears `event.extra`, and attaches an auth UUID; this does not prove that exception messages, URLs, SQL errors or arbitrary log text are PII-free. The support error ring stores a short message/stack/source URL in memory. Confirm production Sentry scrubbing, access and retention.

### Cache/session/tenant switching

- Zustand persistence (`ledgr-app-store`) partializes only theme/sidebar/density/orientation; it does not persist current user/business/membership. This is positive.
- `useAuthListener.purgeAllUserData()` clears store, notifications and in-memory query cache on known identity changes. `wipeIdentityTransitionCaches()` also deletes persisted RQ cache, Workbox `ledgr-api-cache` and enumerated form-draft/session keys; it deliberately preserves accepted financial evidence (`ledgr-offline`, `ledgr_pos_offline_queue`). Identity wipe is awaited on same-tab user switch. The query persister excludes payroll namespaces and mutations, limits size and age, and allowlists query prefixes.
- Business switching (`useAppStore.switchBusiness`) only changes `currentBusiness`; it does not clear caches. Most business data keys reviewed include `businessId` (including dashboard, reports, payroll and construction/manufacturing keys), so keyed cache entries are separated across businesses. Some detail keys omit business id but use globally unique row IDs and server checks; audit this convention as new hooks are added. Never treat key names as security controls.
- Gaps: persisted cache not keyed to authenticated principal, restore begins before auth is resolved, businessId metadata is not populated, and the query key namespace allowlist is not an authorization policy. Startup mismatch and cross-tab/offline transitions need browser-level proof (SEC-04). `PartnerProvider` keys branding by host and a matching localStorage cache; this is public branding/feature-flag context, not a business-client context switch. `partnerClientContext.ts` is absent; no additional client impersonation/switch implementation was found in current source. Partner admin pages query partner roster/usage by partner id; database/RPC must scope the caller, not UI params.

### Route/RBAC/partner checks

- `ProtectedRoute` is auth-only and redirects unauthenticated users; it is not per-feature plan/RBAC enforcement. `PartnerAdminRoute` and platform-admin route hide unauthorized UI but correctly comment that SQL/RPC enforce actual authority. The admin Edge Function rechecks platform-admin status.
- `useCapability` composes plan ∧ partner flag ∧ organisation model ∧ role for visibility/navigation. This is presentation-level; server-side entitlement must exist on write/read paths. Construction has multiple server-side model/plan/capability guards; Manufacturing has the gap in SEC-02.
- Partner RLS: partner admins are read-only over client businesses via policy/view; mutations use platform-admin or partner-admin checks as appropriate. `v_partner_client_usage` is a regular owner-rights view but a later migration `20260727000008_fix_partner_usage_view_isolation.sql` explicitly adds `is_partner_admin(auth.uid(), pc.partner_id)` in the view body. It is not the earlier unscoped version; the fix is confirmed in current migration history. The view still requires live owner/ACL validation.
